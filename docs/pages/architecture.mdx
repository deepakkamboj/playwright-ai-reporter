# Architecture

Playwright AI Reporter is a Node.js reporter package, not a hosted dashboard.
The reporting path runs alongside Playwright; optional providers connect it to
AI services and delivery tools.

<Callout type="info">
    **NOTES:** These diagrams describe the implemented Node.js reporter and its static report artifacts, not a hosted
    SaaS control plane. Methods shown in class diagrams are selected public contracts. On narrow screens, focus a
    diagram and scroll horizontally.
</Callout>

The reporting path does not require connected services. Metadata and API helpers
use Playwright attachments; they do not directly render HTML or create issues.

## Run lifecycle

1. Playwright starts the reporter and supplies workers and project configuration.
2. The reporter records tests, attempts, errors, metadata, and attachments.
3. At run end, it builds failure details, history evidence, and the summary.
4. Enabled AI, issue, and PR workflows run through configured providers.
5. The reporter saves history and JSON; the report generator embeds summary data,
   failure data, CSS, and JavaScript into the standalone Test Health Report.
6. Enabled database and email workflows run after the HTML generation step.

An HTML file being generated is not proof that every optional external workflow succeeded.
Check logs and the actual provider outcome.

## Components and contracts

| Component                      | Responsibility                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------- |
| Reporter                       | Implements Playwright lifecycle callbacks, collects results, and coordinates enabled workflows. |
| `ProviderRegistry`             | Lazily resolves provider instances and holds their lifecycle.                                   |
| Provider factories             | Select implementations and validate provider-specific setup.                                    |
| Provider interfaces            | Define AI, bug-tracker, PR, database, and notification contracts.                               |
| Metadata and recorder helpers  | Attach structured test facts and redacted API evidence through Playwright attachments.          |
| History utilities              | Maintain bounded recent-run evidence for trends and flakiness.                                  |
| Report generator and templates | Render the standalone report and verify its required embedded assets.                           |
| Shard merge utility            | Validate inputs, reconcile run data, and copy referenced evidence.                              |

## Provider boundaries

Providers implement one responsibility. AI completion does not create issues;
the reporter coordinates the AI result with the configured issue or PR provider.
Use the registry rather than directly constructing vendor clients in orchestration code.

Current integrations are listed in [Providers & integrations](/integrations).
PostgreSQL, Slack, and Teams placeholders are not implemented providers.

## Artifact model

- `testSummary.json`: run-level metrics, test records, history evidence, build metadata,
  and the allowlisted configuration snapshot.
- `testFailures.json`: failure details and saved analysis references.
- `test-health-report.html`: embedded data and UI, with relative links for external evidence.
- History file: up to 30 recent runs, stored outside cleaned output when persistence is needed.
- Merged output: combined report data, copied artifacts, and shard provenance.

## Data boundaries

The report UI does not contact an AI service when opened. Enabled generation-time
workflows can send failure details or source to AI services and publish results to
the configured tools.

Built-in redaction handles recognized secret patterns. It does not replace a data
classification policy, private artifact storage, or review of traces and screenshots.
The Settings tab uses an allowlist rather than a dump of the process environment.

## Design concerns and boundaries

| Concern            | Existing design                           | Boundary                                                         |
| ------------------ | ----------------------------------------- | ---------------------------------------------------------------- |
| Portability        | Embedded report CSS, JavaScript, and data | Linked large artifacts still need their files.                   |
| Extensibility      | Five provider interfaces and factories    | Placeholder provider names are not implementations.              |
| Startup work       | Lazy provider resolution                  | Connected workflows still have network and authentication costs. |
| Parallel execution | Validated shard merge and copied evidence | Inputs must be valid and output must be separate.                |
| Privacy            | Shared redaction and allowlisted settings | Application-specific sensitive data still needs review.          |
| Testability        | Typed contracts and replaceable providers | Mocked tests do not prove live provider permissions.             |

## Extending the package

Keep application source and new provider implementations under the source tree,
add focused tests, and update the public documentation for changed contracts.
The docs site is a separate static-export application; it is not included in the
reporter package's runtime dependencies.
