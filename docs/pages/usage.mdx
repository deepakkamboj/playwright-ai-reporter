# Usage

Build a useful report in a small, repeatable workflow: configure output, attach
ownership, record an API call, run the test, and inspect the evidence.

## 1. Install the stable test framework

Use **Node.js 22 or newer** and **Playwright 1.64.0**:

<PackageInstall packages={['@playwright/test@1.64.0', 'playwright-ai-reporter']} dev />

```bash
# package.json (project root)
npx playwright install chromium
```

## 2. Configure reporting and retained evidence

```ts
// playwright.config.ts
import {defineConfig} from '@playwright/test';
import type {ReporterConfig} from 'playwright-ai-reporter';

const reportOptions = {
    outputDir: 'test-results/run',
    historyFile: 'test-results/history.json',
    slowTestThreshold: 5,
    generateFix: false,
    createBug: false,
    generatePR: false,
} satisfies ReporterConfig;

export default defineConfig({
    testDir: './tests',
    outputDir: 'test-results/run',
    retries: 1,
    reporter: [['list'], ['playwright-ai-reporter', reportOptions]],
    use: {
        browserName: 'chromium',
        screenshot: 'only-on-failure',
        trace: 'retain-on-failure',
        video: 'retain-on-failure',
    },
});
```

<Callout type="warning">
    **IMPORTANT:** Playwright cleans its output directory. Keep the persistent history file outside `test-results/run`,
    and publish the whole run directory when linked trace, video, or screenshot files are needed.
</Callout>

## 3. Attach metadata and capture browser API calls

The browser fixture starts recording automatically and attaches evidence during
teardown, including after a failed assertion. This example fulfills its API request
locally, so it needs no application server or external API.

```ts
// tests/report-usage.spec.ts
import {test as base, expect} from '@playwright/test';
import {meta} from 'playwright-ai-reporter/meta';
import {apiRecorderFixture} from 'playwright-ai-reporter/recorder';

const test = base.extend(apiRecorderFixture);

test('account evidence appears in the report', async ({page}) => {
    await meta({owner: 'quality', priority: 'P1', feature: 'account'});
    await page.route('https://reporter.example.test/api/account', (route) =>
        route.fulfill({
            status: 200,
            contentType: 'application/json',
            headers: {'access-control-allow-origin': '*'},
            body: JSON.stringify({name: 'Demo account'}),
        }),
    );
    await page.setContent(`
    <button type="button">Load account</button>
    <p role="status"></p>
    <script>
      document.querySelector("button").addEventListener("click", async () => {
        const response = await fetch("https://reporter.example.test/api/account");
        const account = await response.json();
        document.querySelector('[role="status"]').textContent = account.name;
      });
    </script>
  `);
    await page.getByRole('button', {name: 'Load account'}).click();
    await expect(page.getByRole('status')).toHaveText('Demo account');
});
```

For your real application, replace the local HTML and intercepted endpoint with
your application flow. Keep the recorder active before requests are sent.

## 4. Run and verify the report

```bash
# playwright.config.ts (project root)
npx playwright test tests/report-usage.spec.ts
```

Open `test-results/run/test-health-report.html`. For this single-project example,
a successful run should show:

| Where           | What to verify                                                                   |
| --------------- | -------------------------------------------------------------------------------- |
| **Overview**    | One total test and one passed result.                                            |
| **Tests**       | The account test, its owner, priority, and feature metadata.                     |
| **API results** | A captured `GET` to `/api/account` with status `200` and the demo response body. |
| **Settings**    | Recorded retry settings and disabled optional integration flags.                 |
| **AI fixes**    | No saved analysis, because AI generation is disabled and the test passed.        |

<Callout type="info">
    **NOTES:** Browser capture records fetch/XHR only. For API-only tests, use `recordApiRequest(request).request` or
    the `recordedRequest` fixture. Calls through Playwright's original unwrapped request context are not captured.
</Callout>

See [API & metadata](/api-reference) for manual recording, filters, and shared fixtures.

## 5. Investigate a real failure

1. Reproduce the failure without changing or weakening the assertion.
2. Open the failed test and inspect its error, attempts, metadata, and available artifacts.
3. Compare API status, response, and timing with the expected application behavior.
4. Check **Flaky tests** and history evidence before deciding whether the cause is timing,
   test logic, product behavior, infrastructure, or data.
5. Make a bounded fix and rerun the relevant tests.

Failure artifacts depend on the Playwright `use` settings and what evidence existed
when the test failed. Passing tests do not produce failure-only screenshots or traces.

## 6. Add AI analysis when appropriate

Configure an approved provider in the environment:

```dotenv
# .env (local only; use a secret store for the real key)
AI_PROVIDER=openai
OPENAI_API_KEY=replace-with-your-secret
OPENAI_MODEL=gpt-4o
```

Set `generateFix: true` in `reportOptions`, then rerun a genuinely failing test.
Open **AI fixes** to inspect saved analysis. A passing run is not expected to
generate failure analysis.

<Callout type="warning">
    **IMPORTANT:** AI prompts can include test details and source. Approve that data flow first. Viewing the report
    never applies a suggestion; enable issue creation, PR generation, or other side effects separately and keep human
    review.
</Callout>

## 7. Use the same workflow in CI

Publish `test-results/run/` even if tests fail, restore and save the history file
separately, and let Playwright's exit status determine the test job outcome.
